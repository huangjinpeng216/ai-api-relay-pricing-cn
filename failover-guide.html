一、一个真实的故障长什么样

周三下午，你的客服机器人突然不回消息了。日志里是这样：


15:02:11 POST /v1/chat/completions 200  1.2s
15:02:15 POST /v1/chat/completions 200  1.1s
15:03:40 POST /v1/chat/completions 502  30.0s   ← 开始
15:03:41 POST /v1/chat/completions 502  30.0s
15:03:43 POST /v1/chat/completions 502  30.0s
...（持续 47 分钟）

上游服务商的一个节点挂了。你的代码没有任何 bug，但你的产品在这 47 分钟里是不可用的。

如果这个 API 是你自己直连的官方服务，这种情况概率低但也会发生；如果你用的是第三方中转，概率会明显更高——因为中间多了一层你控制不了的组件。

二、2026 年 10 月的一次真实事故（我亲历的）

这一节不是编的例子，是我在实际监测中遇到的。它展示了故障转移赢不了的那种情况——以及怎么尽早发现。

现象

某个工作日的凌晨，一个第三方 API 中转站突然出现这个状态：

GET /             → 200  （网站能打开，页面正常）
GET /v1/models    → 404  page not found
POST /v1/chat/completions → 404  page not found
POST /api/v1/auth/login   → 404  page not found

网站看起来完全正常，但每一个 API 都返回 404。

为什么这种故障最危险

用户打开网页，一切正常；一调用就报错。第一反应是「是不是我配置错了」，于是开始改 base_url、换 key、重装客户端——折腾半小时才发现是服务方的问题。

而服务方这边，如果只监控「网站能不能打开」，也是完全看不见的。

怎么在外部定位（不需要服务器权限）

我当时手上只有浏览器和 curl，靠三个测试把问题范围切了出来：

测试 1：请求一个必然会失败的路径，看 404 的形态

# 如果返回 HTML，说明是前端兜底
curl -i https://站点/随便什么路径

# 如果返回 "404 page not found" 纯文本，说明请求到了后端框架
curl -i https://站点/v1/models

测试 2：给前缀加倍，验证是不是路径被改写

# 如果反向代理剥掉了 /v1 前缀，那 /v1/v1/models 会被后端当成 /v1/models
curl -i https://站点/v1/v1/models
# 仍然 404 → 说明路径没被改写，问题不在反代

测试 3：用响应头指纹区分不同的后端

# 主应用通常会给页面注入一次性 nonce
curl -I https://站点/          # 看有没有 Content-Security-Policy: ... 'nonce-xxx'
curl -I https://站点/v1/models # 如果这条没有 nonce，说明是另一个后端在处理

就是这一步发现了真相：网站的 API 路径被转发到了一个不是主应用的进程，而主应用本身的 API 路由也没注册（它只会返回前端页面）。

这个案例对故障转移的启示

启示做法
「网站能打开」不等于「服务可用」健康检查要打 API 端点，不是首页
404 比 500 更隐蔽监控判据应是「未鉴权返回 401」，返回 404 就是故障
单站故障转移救不了「全线故障」多站池 + 降级策略都要有
自己也会犯「只监控看得见的指标」的错监控项要对着用户的真实路径设计

所以健康检查应该这么写：

# 正确：打 API 端点，期望 401（未鉴权但路由存在）
curl -o /dev/null -w '%{http_code}\n' https://站点/v1/models
# 401 → 正常
# 404 → 路由丢失，故障
# 000 → 服务不可达

# 错误：只看首页
curl -o /dev/null -w '%{http_code}\n' https://站点/
# 200 只说明 nginx 活着，不代表 API 能用

三、三种处理方式，从便宜到贵

方式一：客户端加重试（最省事，但没用）


for (let i = 0; i < 3; i++) {
  try { return await call(); }
  catch (e) { await sleep(1000 * 2 ** i); }
}

为什么没用：重试解决的是「偶发抖动」，不是「上游挂了」。上游 47 分钟不可用，你重试 3 次花 7 秒，然后照样失败。

重试是必需品，但它不是故障转移。

方式二：代码里写死备用站（有效，但侵入性强）


try {
  return await call(PRIMARY);
} catch {
  return await call(BACKUP);
}

问题：

  • 每个调用点都要写一遍
  • 切过去之后不会切回来（上游恢复了也不知道）
  • 如果备用站 key 换了、额度没了，要改代码重新发布
  • 流式输出时错误可能在**已经输出一半**之后才发生，重试会产生重复内容

方式三：加一层本地代理（多一层，但一次解决）


你的应用 ──► 本地代理 ──► 站点 A
                 ├──────► 站点 B
                 └──────► 站点 C

应用只认一个地址，代理负责选站、切换、回切。应用代码一行不改。

代价是多一跳（本地，通常 <2ms，可忽略）和一个需要维护的进程。

四、设计这一层时，最关键的是「什么该切，什么不该切」

这是我踩过最深的坑。一开始我写的是「任何错误都切下一家」，结果：

场景无脑切换的后果
客户端发了个格式错误的请求（400）三个站各失败一次，浪费三倍时间，最后还是 400
key 过期（401）切到备用站也报 401（如果你三个站用同一把 key），纯浪费
触发限流（429）切下一家确实能过，但如果三家都限流，就是三倍消耗
上游 5xx✅ 该切
连接超时✅ 该切
流式中途断流✅ 该切，但要处理已输出的部分

正确的判断表：

状态码处理理由
5xx切下一家上游自己的问题
超时 / 连接失败切下一家网络或上游问题
401 / 403直接返回key 问题，换站解决不了
429直接返回（或退避后重试同一家）切站会放大消耗，且容易被判定为滥用
其他 4xx直接返回请求本身有问题，换谁都没用

这条规则写进代码只需要几个 if，但它决定了你的代理是「有用」还是「有害」。

五、还有一个隐蔽问题：失败了要不要标记

「这次失败了就永久不用它」和「这次失败了下秒还用它」都不对。

我最后用的策略是连续失败计数 + 冷却期：


连续失败 1 次  → 记一笔，继续用
连续失败 2 次  → 记一笔，继续用
连续失败 3 次  → 进入冷却 60 秒，期间不分配流量
冷却期结束    → 重新试用，成功则计数清零

为什么是「连续」而不是「累计」：累计计数会让一个偶发失败的站永远翻不了身；连续计数能区分「偶尔抽风」和「真的挂了」。

为什么要有冷却而不是直接剔除：上游会恢复。你不给它恢复的机会，就等于永久损失一个节点。

六、流式输出是最麻烦的部分

非流式请求失败很好处理——重发就行。流式不一样：


data: {"choices":[{"delta":{"content":"今天"}}]}
data: {"choices":[{"delta":{"content":"天气"}}]}
                                    ← 连接断了

这时候用户屏幕上已经有「今天天气」了。你重发整个请求，用户会看到「今天天气今天天气不错」。

处理方式有两种：

1. 不重发：把已输出的内容当作部分结果返回，告诉用户「响应中断」，让上层决定是否重试

2. 续写：把已输出内容作为 assistant 消息塞回上下文，让模型接着写

我在实现里选了第一种——因为在代理层做「智能续写」会引入新的不确定行为，而代理的定位应该是透明。

七、自己实现的话，最小可用版本长什么样

我写了一个，8KB，零依赖（只用 Node 内置模块）。核心就三件事：


// 1. 按权重挑顺序
const seq = orderedUpstreams();

// 2. 逐个尝试，5xx/超时才切
for (const u of seq) {
  try {
    const res = await forward(u, req, body);
    if (res.statusCode >= 500) { markFail(u); continue; }
    if (res.statusCode === 401) return passthrough(res);  // 不切
    markSuccess(u);
    return pipe(res);
  } catch (e) {
    markFail(u); continue;
  }
}

// 3. 全挂了返回 502，并说明每家的失败原因
return json502(errors);

配套的 /health 接口能看每家可用率和连续失败数：


{
  "ok": true,
  "upstreams": [
    { "name": "primary",  "available": true,  "fails": 0, "successRate": 0.997 },
    { "name": "backup-a", "available": false, "fails": 3, "cooldownSeconds": 42 }
  ]
}

八、两个实现时踩的坑（别人大概也会踩）

坑一：`content-length` 和 `transfer-encoding` 同时存在

代理转发时把请求体读成了完整 buffer，就应该用 content-length 重发。如果同时保留了原始的 transfer-encoding: chunked，上游服务器会直接返回 400，而且不会告诉你原因。

我在这上面浪费了半小时，最后是打印上游收到的原始请求才发现的。

坑二：base_url 重复拼接

用户的配置里 baseUrl 常常已经带 /v1（比如 https://site/v1），而客户端请求的路径也带 /v1（/v1/chat/completions）。直接拼接变成 /v1/v1/chat/completions → 全部 404。

修法是拼接前做一次前缀去重。

九、要不要自己做一个

三个判断标准：

你的情况建议
只用一个站，偶尔失败，能接受短暂不可用客户端重试够了，别加复杂度
余额分散在几家，手动切换嫌麻烦值得做一层代理
面向用户的产品，不可用会掉客户必须做，而且要考虑的不止是切换

第三种情况我要多说一句：代理层解决的是「上游挂了自动切」，但解决不了「所有上游都挂了」。真到了那一步，你需要的是「降级策略」——比如用小模型顶上、或者直接告诉用户「稍后再试」，而不是让请求卡在那里转圈。

十一、最后一句

故障转移不是什么高深技术，一个下午就能写完。但它解决的是一类会持续发生、且发生时你毫无准备的问题。

如果你现在正在用第三方 API 做东西，我建议你至少想一遍：

如果这个站明天早上打不开了，我的应用会怎样？

想清楚这个问题的答案，比读十篇工具推荐都有用。
