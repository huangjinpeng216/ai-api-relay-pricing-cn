API 并发与限流怎么处理

429 的真实含义 · 指数退避 · 批量任务节奏 · 流式中断重连　｜返回比价指南

先分清两件事：限流（rate limit）是「你太快了」，稍等就能过；额度耗尽（quota）是「你没钱了」，重试多少次都没用。看到 429 先做这个判断，否则会白白重试几百次。

一、并发和 QPS 不是一回事

概念含义常见限制形式
并发（concurrency）同一时刻有 N 个请求在处理「最多 5 路并发」
QPS / RPM每秒 / 每分钟发出的请求数「60 次/分钟」
TPM每分钟消耗的 token 数「10 万 token/分钟」

很多服务商同时限制这三项。你的程序看起来很慢，可能不是网络慢，而是被 TPM 卡住了。

二、429 的三种真实原因

  1. 真的太快：瞬时并发或 RPM 超限。→ 加退避重试即可。
  2. 额度不足被软拒绝：部分中转站余额低时会返回 429 而不是 402。→ 查余额。
  3. 上游共池拥塞：同池其他用户流量大到影响你。→ 换模型或错峰。

区分方法：看响应体里的 error.message，以及重试后是否稳定复现。稳定复现 + 换个时间段也一样 → 大概率不是你的问题。

三、正确的重试写法：指数退避 + 抖动

async function callWithRetry(fn, maxRetries = 5) {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fn();
    } catch (e) {
      const status = e.status || e.response?.status;
      // 只有限流和 5xx 才值得重试
      if (status !== 429 && !(status >= 500 && status < 600)) throw e;
      if (attempt === maxRetries) throw e;

      const base = 1000 * 2 ** attempt;        // 1s, 2s, 4s, 8s...
      const jitter = Math.random() * 400;      // 抖动，避免同时重试
      await new Promise(r => setTimeout(r, base + jitter));
    }
  }
}

关键点：

  • 只对 429 和 5xx 重试，400/401/403/404 重试毫无意义
  • 必须加抖动（jitter），否则所有客户端会在同一秒一起重试，形成二次雪崩
  • 重试要有上限，避免死循环烧钱

四、批量任务：用队列 + 令牌桶控制节奏

// 简单做法：固定并发 + 每条之间留间隔
const limit = 3;          // 并发数
const gap = 200;          // 每条之间的间隔 ms
const queue = [...tasks];

async function worker() {
  while (queue.length) {
    const task = queue.shift();
    if (!task) break;
    await callWithRetry(() => run(task));
    await new Promise(r => setTimeout(r, gap));
  }
}

await Promise.all(Array.from({ length: limit }, worker));

经验值：从 2～3 并发 + 200ms 间隔起步，观察 429 率。低于 1% 就可以往上加；超过 5% 就降回来。

五、流式请求中断怎么办

现象原因处理
输出到一半断开代理层超时、网络抖动捕获中断，从已生成内容后继续（把已有输出作为 assistant 消息续写）
一直没有数据返回首字延迟高，或 SSE 未透传加读超时（如 60s），超时后降级为非流式
报 SSE 解析错误客户端没处理 data: [DONE] 或空行按行解析，忽略空行与注释行

六、比限流更贵的两个坑

  • 无上限重试烧钱。失败请求在上游可能仍计费。务必设最大重试次数和每日预算。
  • 并发开太大反而更慢。上游排队后延迟上升，成功率下降，总耗时反而更长。
