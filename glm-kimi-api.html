二、模型名怎么写

调用时必须用站点列出的准确名称。常见写法（以各站公示为准）：

glm-5.3
glm-5.3-flash
kimi-k3

注意大小写和连字符。自己猜的名字会直接报 model not found，报错排查见 报错大全。

三、调用示例（OpenAI 兼容格式）

curl https://你的站点/v1/chat/completions \
  -H "Authorization: Bearer sk-xxx" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "glm-5.3",
    "messages": [
      {"role": "user", "content": "把下面这段改成正式的公文体"}
    ]
  }'

换成 Kimi 只需把 model 改成 kimi-k3，其余不变。

四、长文档任务怎么用 Kimi

长上下文的正确用法不是「把整个 PDF 塞进去问一句」。更省钱也更准的做法：

  1. 先分段摘要：逐章生成摘要，再把摘要合并
  2. 只喂相关片段：先用关键词检索定位到相关段落
  3. 明确输出结构：告诉它要表格还是分点，能显著减少输出 token

这样即使上下文窗口很大，也能把单次成本压下来。

七、长上下文能装多少内容

「上下文窗口 100 万 token」听起来很能装，换算成实际内容是这样：

内容类型大致 token 数能装多少
中文文档1 汉字 ≈ 1.5 token100 万 token ≈ 60 万字
英文文档1 单词 ≈ 1.3 token100 万 token ≈ 75 万词
一本 300 页的书约 15～25 万 token能同时装 3～5 本
合同 / 财报 PDF约 3～8 万 token能装十几份

注意：上下文窗口 ≠ 你应该用的量。装得越多，单次成本越高，而且模型在超长上下文里的召回率会下降，不一定答得更准。

八、流式输出怎么开

长文档任务的响应时间通常较长，不开流式会以为程序卡死了。OpenAI 兼容格式下加一个参数：

{
  "model": "kimi-k3",
  "messages": [...],
  "stream": true
}

开启后服务端会持续推送数据块，客户端要按行解析，并处理结束标记。不做流式的话，长输入可能要等几十秒才有第一个字节。

十、常见问题

Q：GLM 和 Kimi 能同时用吗？

通常可以，而且推荐。大模型平台一般支持同一账号下调用多个模型，按任务切换即可——写文案用 GLM，读长文档切 Kimi。前提是你用的平台确实上架了这两个模型。

Q：模型名在不同平台叫法一样吗？

不一定。有的平台会加后缀（如 -flash、-pro）或改大小写。规则是以你所用平台的模型列表为准，不要照抄别处的名字。

Q：长文档任务失败了怎么办？

先看报错码。context_length_exceeded 说明超窗口了，需要分段；429 是限流，加退避重试；超时的话改流式或降低单次输入量。详细对照表见 报错大全。

Q：中文任务一定要用 GLM 吗？

不一定。通用模型的中文能力已经不错，GLM 的优势主要在公文、术语统一、正式文体这类风格要求高的场景。日常问答用什么模型差别不大。

十一、接入第三方网关时注意

  • 确认站点同时支持你需要的模型，不要只看有一个
  • 确认模型名与站点列表一致，不同站可能命名略有差别
  • 长文本任务要留意站点是否有单请求 token 上限
  • 批量任务前先跑 10 次，看延迟分布和失败率
